Catch risky offline payments before they sync. And show the evidence.

MeshShield is a local research simulator for an offline payment network. It generates delayed, duplicate and tampered payments, checks their integrity, builds time-aware features and scores risk, then explains every flag.

    This simulator runs in your browser and mimics MeshShield’s integrity checks, velocity features and a logistic-style risk score. The weights are illustrative; the real model is trained in Python on a chronological split.

    Three steps. One payment trail.

    Every transaction is generated, checked and scored in order, using only what was known at the time it happened.

    1. Generate

    A seeded generator creates 1,600 synthetic payments with event time and arrival time, then delays, duplicates and reorders the sync.

    normal 85%high amountshared devicereplaybad signature

    2. Check integrity

    Hard rules run first and stay separate from the model: duplicate IDs, replayed events, invalid signatures and impossible fields.

    SQLite accepts each event ID once

    3. Score risk

    Features come from earlier history only. A standardized logistic regression returns a risk score and the inputs that pushed it up.

    amount, timevelocitygraph
    11 features, 2 from the device graph

    Every flag comes with evidence.

    MeshShield keeps two kinds of evidence apart. This panel shows the latest payment from the simulator above.

    Integrity findings
    Direct checks, like a failed signature or a repeated event ID. They can send a payment to review on their own.
    Model contributions
    Associations learned from training data. They show what moved the score, not what caused fraud.
    Point-in-time
    Velocity and device counts use earlier event times only. The current payment joins history after its features are recorded.

    When sync arrives late, nothing breaks.

    Payments queue offline and arrive late, out of order or twice. Event time and ingestion time stay separate, so delays never leak into history.

    Idempotency
    SQLite stores each event ID once. A retried delivery is ignored, not applied twice.
    Delivery simulation
    Saved seed-2025 run: 1,695 deliveries, 1,487 accepted, 122 duplicates ignored, 86 invalid signatures rejected.
    Replay demo
    POST /api/replay delivers the same event twice and shows the second is refused.

    Event outcomes

    1. acceptedFirst delivery with a valid signature. Stored once.
    2. duplicateSame event ID again. Ignored, counted, never re-applied.
    3. rejectedSignature check failed. Never reaches the store.

    A reproducible demo, start to finish.

    Python 3.11 or newer. Runtime code uses only the standard library.

    1. 1Create an environment

      py -3 -m venv .venv; .\.venv\Scripts\Activate.ps1

    2. 2Generate, train and evaluate

      .\scripts\run.ps1 demo

      On macOS or Linux: PYTHONPATH=src python -m meshshield.cli demo

    3. 3Open the dashboard

      .\scripts\run.ps1 serve

      Then visit http://127.0.0.1:8000. Keep it local; it has no authentication.

    Built to be understood.

    MeshShield is for learning how offline payment risk review works, not for moving money.

    In scope

    • Seeded synthetic payments and a dataset card
    • Signature, duplicate and replay checks
    • Leak-free chronological evaluation
    • Logistic baseline vs graph features vs rules
    • Local dashboard and JSON API

    Out of scope

    • Authorizing or settling real payments
    • Real fraud labels or real customer data
    • Network-facing deployment
    • Real cryptographic signatures, for now
    • Claims about real-world accuracy

    Questions.

    Does it move real money?

    No. It never authorizes or settles anything, and its scores must not drive real account decisions.

    Is the fraud real?

    No. Labels are scenarios chosen by the generator, so metrics measure how well the model recovers those patterns.

    Why do graph features not win yet?

    The synthetic graph signal is weak and the test set has only 46 positives. A stronger generator or real datasets are the next step.

    What happens to a duplicate delivery?

    SQLite accepts each event ID once, so a retry is ignored and counted as a duplicate.

    Do I need to install anything?

    Only Python 3.11 or newer. ReportLab is optional, and only for rebuilding the PDF guide.
